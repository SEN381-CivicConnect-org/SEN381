Technology-Stack Decision

PED v2.0 §6.4 — ADR-004. Formally resolves FEC-01 and confirms the runtime the architecture (§6.2) and persistence boundary (§6.3) are built on.

After careful research, team discussion and evaluating the functional and non-functional requirements, the team has decided to use the ASP.NET tech stack, using Blazor, PostgreSQL and Docker. This stack keeps the project in one language instead of splitting it across many — such as JavaScript/React for the front end — which maximises team capability, maintainability and deployment consistency, and avoids licensing costs.

These technology selections, along with their associated ecosystem risks and version dependencies, are formally documented as ADR-004 (Technology Stack Selection). Risks regarding the container-orchestration learning curve and PostgreSQL migration management have been added to the Risk Register.

Language: C# (.NET 10 LTS)

C# (.NET 10 LTS) is the foundation of the CivicConnect platform. It is strongly typed and suits object-oriented programming, which works well for Blazor and ASP.NET Core, and removes the need for a fragmented, multi-language codebase.

Comparison

A unified C# stack was chosen over a multi-language stack that might have used a Python backend, JavaScript frontend and MongoDB database, to reduce context-switching and make the learning curve for Blazor and ASP.NET Core easier for the development team.

How C# fits into the project
  • Team capability and reduced context switching: the language fits the team's capability and the schedule constraint. Standardising on C# means the team does not switch languages for different features, which accelerates development and reduces the learning curve.
  • Maintainability and code sharing: using C# end-to-end lets the team share domains, data transfer objects (DTOs) and validation rules directly between client and server, reducing duplicate code and increasing maintainability for future changes.
  • Meaningful peer review: the project requires progressive, authentic collaboration with meaningful peer review for substantive changes. A single-language stack means any of the three team members can effectively review both frontend and backend Pull Requests, preventing knowledge silos where only one person understands a specific layer of the application.

Front-end: Blazor WebAssembly

Blazor uses C# — the language of this tech stack — to run natively within the browser, eliminating the use of JavaScript. It runs on WebAssembly, so .NET runs directly on the client.

Comparison

Blazor was chosen over tools like React.js or Angular, because either would result in a mix of C# and JavaScript, introducing dependency-management overhead and a fractured toolchain.

How Blazor fits into the project
  • Immediate user feedback: when an incident is updated, the backend API commits the change to the database and publishes an asynchronous event to the message broker, then returns a 200 OK to Blazor. This decoupled, asynchronous approach lets all systems operate independently without waiting on each other.
  • Usability through upfront validation: the frontend gives users an interactable platform. To prevent garbage-in-garbage-out, validation is set up on input fields, and Blazor handles this with drop-down boxes and inline validation that asks users to re-enter invalid input.
  • Strict security boundaries: relying solely on client-side validation is a security risk, since a malicious actor could bypass client-side rules. Blazor therefore acts only as a user-experience tool, while the core service layer and database remain the final backstop for business rules and data constraints.

Backend/Runtime: ASP.NET Core

ASP.NET Core integrates well with C#, provides a robust, cross-platform runtime for the APIs, and lets the team build a centralised, testable service layer that natively supports the Docker containerisation strategy.

Comparison

ASP.NET Core was chosen over database-level stored procedures or procedural SQL triggers, because it keeps domain rules in highly testable, version-controlled C# rather than hiding them in vendor-locked database logic.

How ASP.NET Core fits into the project
  • Centralised business logic: ASP.NET Core lets the team enforce complex, multi-entity business rules — priority calculations and parent-incident matching — at the application layer, keeping domain logic in memory where it is highly testable via service stubs, avoiding the complexity, poor reviewability and vendor lock-in of database-level stored procedures.
  • Explicit orchestration: the API controller acts as a central orchestrator for mandatory status transitions, handling validation, writing the initial row, and the database transaction, so the core sequence of events and failure handling stays explicit, predictable and easy to trace (see DD-01).
  • Transactional boundaries: the service executes operations as a single server-side transaction per submission, enforcing atomicity.
  • Resilience under load: while the system is under significant strain from multiple users, the API protects its worker thread pool by offloading notification tasks to the message broker. Using asynchronous events instead of waiting for HTTP calls avoids an extended I/O wait state, so the API stays available to new citizen requests without crashing.

Database: PostgreSQL 16

PostgreSQL provides robust transaction atomicity and rigorous schema-level constraint enforcement, serving as a reliable foundation for protecting data integrity against concurrent access, complementing the C# backend by handling strict data rules while leaving complex business logic to the application layer.

Comparison

PostgreSQL was selected over a NoSQL alternative (such as MongoDB) to formally resolve FEC-01. CivicConnect's data requires strict referential integrity, structured reporting, and complex ticket relationships that relational SQL handles best. See the full comparison against document-store, polyglot, SQLite, MySQL/MariaDB and SQL Server alternatives in docs/data-persistence/persistence-integrity-and-scaling-V1.0.html.

How PostgreSQL fits into the project
  • Guaranteed atomicity: every ticket submission runs in one server-side transaction, so the whole transaction succeeds or fails completely, fulfilling the atomicity requirement.
  • Schema-level constraints: PostgreSQL schema constraints enforce concurrency-access rules and second-writer conflicts.
  • Idempotency protection: to resolve duplicate submissions from repeated clicks, PostgreSQL enforces unique constraints on the idempotency key, catching duplicate requests at write time and preventing redundant tickets from being processed.
  • Optimistic concurrency: every mutable aggregate root carries a version column, checked and incremented on every update (see docs/data-persistence/persistence-integrity-and-scaling-V1.0.html §5, "Standing rules"). This closes the open item noted in the M2 source material.
  • Referential integrity: foreign keys on every table ensure subscriptions, child tickets, and status histories always point to incident rows that actually exist, protecting the application from orphaned records.

Deployment & Build: Docker

Docker is the standard for containerisation and build tooling (free Docker Engine licence).

Comparison

Docker was chosen over bare-metal VM deployments because it packages the API, Blazor client, and PostgreSQL database into immutable images, eliminating "it works on my machine" discrepancies.

How Docker fits into the project
  • Deployment compatibility: Docker ensures complete environment parity between local development machines, automated testing pipelines, and remote staging environments.
  • Configuration isolation: environment variables passed into the containers decouple sensitive configuration and secrets from the source code, adhering to the strict security constraints in NFR-01 and ASR-04.
