Initial Design Decisions

PED v2.0 §6.5. Two CivicConnect design problems carried from Assignment 2 findings into concrete project decisions, each stating the problem, the alternatives, the decision, the rationale, and the software elements affected.

Evidence boundary

The current repository evidence reviewed for this work does not yet show implementation of these decisions in application code. This document states decisions and their rationale, not implementation evidence. Branch/class/PR/test references will be added once development reaches these areas.

Design Context and Decision Principles

The M1 baseline involves controlled transition of ticket statuses, recording actions, comments, resolutions, providing requester feedback, and having auditability over the request history. These needs present an architectural question: how to coordinate status-change behaviour without one service gaining unrelated responsibilities.

The M1 baseline also establishes CivicConnect as a configurable office ticket management system. Controlled categories, classification, organisational processing and roles are supported; a generic no-code workflow engine, arbitrary fields, scripting, and enterprise multi-tenancy are out of scope.

The decision lenses used were cohesion, controlled coupling, and SOLID principles. Patterns and interfaces were not assumed to automatically produce better design, and any added layer of indirection needed a reason grounded in some kind of expected change or variability (Budgen, 2021; Martin, 2003).

DD-01 — Controlled Ticket Status Reactions

Design problem

Changing the status of a ticket can be more than simply changing the status field. CivicConnect may require validation of the transition, storage of the new state, audit/history recording, and requester notification. Putting every existing and future reaction into one method of a TicketService class risks that service becoming an "everything happens here" class.

Alternatives considered
AlternativeStrength for CivicConnectMain trade-off / risk
Explicit orchestration Required operations and sequencing remain visible and predictable. Strong fit for persistence, audit/history and other consistency-critical work. The orchestrator can grow into an "everything happens here" service if independent reactions continue to accumulate.
Observer Separates independently changing reactions from core transition logic and allows new observers without directly editing the transition service (Gamma et al., 1994). Introduces indirection, registration/dispatch complexity, possible uncertainty around order/failure handling, and additional integration-test needs.
Project-specific decision

For mandatory status transition behaviours, use explicit application-service orchestration. For observer-type event processing, apply it exclusively for confirmed secondary responses, which can independently vary and do not affect the primary transition outcome.

This ensures that transition validation, persistence, and mandatory audit/history behaviour stay explicit. If the transition is successful, it might publish a domain/application event internally after the consistency-sensitive part is done. Other secondary effects — like notifying the requester, if such functionality is present — could be made through subscription to that event.

Rationale, expected benefit and trade-off

Rationale: the choice retains visibility of control for correctness-dependent ticket behaviour while defining the extension point only where variability exists independently.

Expected benefit: cohesion in the ticket-transition logic, better coupling to the mandatory collaborators, and the option to append independent actions without constantly modifying the transition logic itself.

Complexity introduced: Observer needs event dispatching/registration, failure semantics, ordering assumptions and integration tests. This extra complexity does not make sense if there are just a few reactions or if they are transactional (Gamma et al., 1994).

SOLID/design link: SRP provides for the separation of independently varying reactions; OCP becomes applicable only where repeated extensions are demonstrated. Necessary dependencies are maintained explicitly without abstracting only for the purpose of applying a pattern (Martin, 2003).

Affected software elements
  • Ticket application/service layer
  • Ticket status-transition validation/policy
  • Ticket repository or persistence boundary
  • Request history/audit recording
  • Optional internal event publisher/dispatcher
  • Secondary reaction handlers such as requester feedback/notifications when implemented

DD-02 — Controlled Office Configuration

Design problem

CivicConnect needs to be configurable for offices without being separately coded for every office. Categories, classifications, organisational areas, and role-based configuration can differ, but the ticket management cycle stays the same. Hard-coding every office's values in controllers/services disperses the changes; a fully generic strategy for every configurable aspect would take CivicConnect out of its scope.

Alternatives considered
AlternativeStrength for CivicConnectMain trade-off / risk
Controlled configuration Validates office differences through data and assigns a role to the configuration. The core ticket service uses supported configuration, not hard-coded office values. Needs configuration validation, authorisation, persistence, and careful boundaries so invalid configuration does not adversely affect ticket operation or history.
Strategy Packs two very different algorithms under one contract, letting the program choose what it wants to do at runtime (Gamma et al., 1994). Introduces a strategy interface and strategy selector; inappropriate when an office uses the same strategy with different data rather than different behaviour.
Project-specific decision

Use controlled data-driven configuration as the default strategy for office-specific differences. Do not use Strategy for Categories, Roles, Classifications or Organizational Areas unless further development shows different algorithms or policies which cannot be encoded as configuration data.

A specific configuration role is responsible for configuration validation and access to supported configuration. Components performing ticket processing use that controlled configuration but keep a single ticket workflow. This fits the M1 configuration boundary, since CivicConnect is reusable across offices but is not a generic workflow builder or no-code platform.

Rationale, expected benefit and trade-off

Rationale: the current office differences identified are more about values in a controlled envelope than alternative algorithms, so treating them as configuration keeps the design balanced.

Expected benefit: values for the office can be modified without altering the underlying ticket-processing program logic; configuration values stay consistent, and there are no redundant office-specific branches within the application.

Complexity introduced: the team must provide validation, authorization, persistence, and proper history of configuration changes, with defined constraints so configuration cannot become a user-authored workflow.

Strategy deferment: Strategy remains a viable future option provided there is evidence of significant variation of algorithms, like a different approach to prioritization or routing. Otherwise, the configuration approach is used (Gamma et al., 1994).

Affected software elements
  • Administration/configuration UI or endpoints
  • Configuration service/module
  • Category and classification configuration
  • Role/authorisation configuration boundary
  • Organisational area/team configuration
  • Ticket services that consume validated configuration
  • Configuration persistence and audit/history rules
