2.1 Scope Statement v2.0

Baseline Version: 2.0 (Milestone 4 Final Operational Baseline) | Baseline Reference: SEN381 Master Project Brief §2, §6, §17–§21

Milestone 4 Scope Baseline Evolution

This Scope Statement v2.0 extends and finalizes the Milestone 1 Scope Baseline (preserved at scope-statement-V1.0.html). It reflects the complete delivery, verification, and operational readiness of the CivicConnect platform across all four project milestones.

1. Platform Purpose & Operational Context

CivicConnect is engineered as an access-controlled, configurable municipal service request and incident tracking platform. It replaces fragmented, uncontrolled municipal communication practices — including ad-hoc WhatsApp messages, unindexed emails, telephone calls, scattered spreadsheets, and paper records — with an authoritative, traceable, and audited ticket lifecycle platform.

The platform provides unified service request intake, automated incident clustering, deterministic priority calculation, role-isolated triaging queues, ongoing commentary, asset replacement tracking, automated citizen notifications, and analytical management oversight while remaining strictly bounded against unnecessary enterprise complexity.

2. Architectural & Deployment Scope

Relational Core Persistence

Single PostgreSQL 15 engine with citext email uniqueness, timestamptz UTC timestamps, partial unique clustering indexes, and optimistic version concurrency tokens.

Separation of Concerns

ASP.NET Core Web API (port 5060) providing business endpoints; Blazor Web App (port 8085) providing interactive, responsive role-based user interfaces.

Asynchronous Messaging Seam

Store-and-forward notification queue boundary via RabbitMQ (with resilient in-process fallback), decoupling database transactions from carrier latency.

Production Deployment & DR

Deployable via Docker Compose multi-container topology and Render Infrastructure as Code (render.yaml). Verified disaster recovery restore drill RTO of 12.27 seconds.

3. Multi-Role Organizational Boundary

CivicConnect serves one municipal organization per deployed container stack (single-tenant per deployment), accommodating distinct operational personas without cross-role leakage:

  • Citizens / Requesters: Self-service submission, category selection, real-time status tracking, private ticket history with cryptographic ownership isolation, and automated notifications.
  • Technicians / Service Staff: Department-isolated queues, unassigned ticket claiming, supervisor delegation, controlled lifecycle state transitions, ongoing progress notes, and asset-linked resolutions.
  • Supervisors & Operations Managers: Triage oversight, SLA overdue tracking, priority overrides with mandatory justification, categorical and team turnaround reporting, and append-only audit inspection.
  • System Administrators: Controlled category catalogue configuration, location hierarchy maintenance, SLA priority targets, and user/role administration.

4. Regulatory Compliance & Least Privilege Scope

In accordance with the Protection of Personal Information Act (POPIA Act 4 of 2013), the scope incorporates strict statutory privacy protections:

  • POPIA s14(1) Retention & Disposal: Automated sweeps purge expired idempotency keys (>7 days) and aged read notifications (>12 months), while de-identifying personal data on user retirement while preserving incident referential integrity (NFR-05).
  • POPIA s19(1) Staff Information Protection: The keyless staff_directory database security view exposes safe staff names and team roles while omitting password hashes and personal contact details (NFR-04).
  • Database Least Privilege: Three distinct PostgreSQL database roles (civic_app for runtime DML, civic_migrate for ephemeral DDL migrations, and civic_report for read-only access) enforce separation of duties at the database catalog level (NFR-10).
