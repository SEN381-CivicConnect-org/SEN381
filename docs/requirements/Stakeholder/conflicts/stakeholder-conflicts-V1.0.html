Details

STK-CFL-01 — Self-declared urgency vs. a pre-populated ticket queue

Conflict

All users reporting an issue (STK-01) will want their issue to take top priority; however, technicians (STK-02) will already have a pre-populated ticket queue. The problem is that if urgency is self-declared, everything will be declared urgent.

Solution

Have priority calculated off impact and urgency, using the reported location and category. However, an override will still exist for the team supervisor (STK-03) to exert human discretion, with a recorded reason.

STK-CFL-02 — Mass reportable incidents

Conflict

When the network drops or a similar mass reportable incident takes place, every user that reports the incident (STK-01) wants their report to be acknowledged, but the technicians (STK-02) want to resolve only one incident.

Solution

Cluster related reports into a parent incident and subscribe every reporter to it. Each person keeps their own reference and receives updates, but technicians (STK-02) only work with one item.

STK-CFL-03 — Closure speed vs. traceability of goods

Conflict

Technicians (STK-02) want to resolve a ticket as quickly as possible with minimal typing, whereas the finance department (STK-05) wants a detailed report with as much traceability to physical goods and hardware as possible, to track faulty goods that need to be replaced or to notify suppliers about faulty equipment.

Solution

Make the report a technician (STK-02) must fill in as concise as possible while retaining all relevant and important data.

STK-CFL-04 — Visibility of unresolved incidents

Conflict

Users (STK-01) want reports that were already made to be visible, whereas the operations manager (STK-04) would prefer not to display a list of unresolved issues.

Solution

Publish unresolved incidents, as the argument for publishing the data is stronger than the argument against. It is also possible to publish resolution statistics per category.
