3.1 Functional Requirements

ID Requirement Source Statement Acceptance Criteria
FR-01 Submit and Categorise a Service Request Requested Capabilities The system will allow authorised users to submit a ticket request and categorise it using a controlled category mechanism. Given that a user has entered the required issue details and selected a category for their request, when the request is submitted, a new ticket should be generated containing the information from the request and a success confirmation message should be displayed.
FR-02 Log into the appropriate user portal Minimum Business Capabilities The user should enter their details into a login screen, which should redirect them to their user portal if their credentials were correct, where they can now access their user functions Given they enter the correct credentials, a request to the backend should be made to check their entered credentials in the database; if their details are found, a success response should be sent back, and finally the user should be redirected to their portal
FR-03 Cluster Duplicate Reports and Subscribe Every Reporter Stakeholder conflict (STK-CFL-02) The system will attach a new service request to the existing open incident for the same category and location where one exists, create that incident where none exists, and subscribe the reporter to the incident in either case, while preserving the reporter's own request reference. Given an open incident already exists for category "Network outage" and location "First Floor", when a second user submits a request for the same category and location, then no second incident is created, the existing incident's report count increases by one, the second user receives their own distinct request reference, and the second user appears exactly once in the subscriber list for that incident.
FR-04 Assign or Claim Request Ownership Staff capabilities The system will allow an authorised staff member to explicitly claim an unassigned request, or a supervisor to assign a request to a specific staff member, establishing a recorded owner for the incident. Given an unassigned request in the active queue, when a staff member clicks "Claim", then the request is assigned to them and moves to their personal queue; and given an unassigned request, when a supervisor selects "Technician B" from the assignment dropdown, then the system records Technician B as the owner and an entry is added to the audit history.
FR-05 Calculate Priority from Impact and Urgency Stakeholder conflict (STK-CFL-01) The system will calculate incident priority from the impact level of the reported location and the urgency level of the selected category, and will record the impact and urgency values used at the time of calculation. Given category "Electrical" has urgency level 1 and location "Ground Floor" has impact level 2, when a request is submitted for that category and location, then the incident stores priority as the value produced by the documented calculation for (impact 2, urgency 1), and stores impact level 2 and urgency level 1 alongside it; and given an administrator subsequently changes the category's urgency level to 4, when the incident is retrieved, then its stored priority, impact level and urgency level are unchanged.
FR-06 Supervisor Priority Override with a Recorded Reason Stakeholder conflict (STK-CFL-01) The system will allow a team supervisor to override a calculated incident priority, and will reject any override that does not carry a reason, recording the reason, the supervisor and the time of the override. Given an incident with calculated priority 3, when a team supervisor sets priority 1 with the reason "Board meeting in this room at 14:00", then the incident shows priority 1, the calculated priority remains visible as 3, and the reason, the supervisor's identity and the override timestamp are stored and displayed; and when a supervisor attempts an override with an empty reason, then the request is rejected and the priority is unchanged.
FR-07 Controlled Status Transitions with a Complete History FEC-01; Staff capabilities The system will permit only the documented status transitions for an incident, will reject every other transition, and will record one history entry per accepted transition identifying the previous status, the new status, the actor and the time. Given an incident with status "NEW", when an authorised technician claims it, then its status becomes "ASSIGNED" and exactly one history entry is recorded showing NEW → ASSIGNED with the technician's identity and a timestamp; and given an incident with status "NEW", when any user attempts to set its status directly to "RESOLVED", then the request is rejected with an explanatory message, the status remains "NEW", and no history entry is created.
FR-08 Auditable Record of Changes Management and oversight capabilities (PED §2); POPIA s17 The system will record an audit entry for every create, update, status change, priority override, merge, configuration deactivation and role grant, identifying the actor, the entity, the action, the time and the changed values, excluding credentials and personal contact details from the recorded values. Given a supervisor overrides an incident's priority, when a manager opens that incident's audit trail, then an entry with action "OVERRIDE" is listed showing the supervisor, the time, the previous priority and the new priority; and given any audit entry for a user record, when its stored values are inspected, then no password hash and no e-mail address appear in them.
FR-09 Configuration Deactivation Preserves History Configuration and administration capabilities (PED §2) The system will allow an authorised administrator to deactivate a category, location, service team or asset so that it can no longer be selected on new requests, while leaving all existing requests, incidents and history that reference it unchanged and readable. Given category "Printing" is referenced by 12 existing incidents, when an administrator deactivates it, then the deactivation is recorded with the administrator's identity and the time, the category no longer appears in the submission form's category list, all 12 incidents still display "Printing" as their category, and their history and audit entries are unchanged; and when the administrator attempts to delete the category outright, then the request is refused.
FR-10 Asset Linkage on Resolution Stakeholder conflict STK-CFL-03 (PED §1.3.3); finance department (PED §1) The system will capture a resolution as a resolution code, a concise summary and, where the resolution indicates that equipment must be replaced, a reference to the specific asset, and will reject a replacement resolution that does not identify an asset. Given a technician resolves an incident with code "REPLACED" and does not select an asset, when the resolution is submitted, then it is rejected with a message requiring an asset and the incident's status is unchanged; and given the technician selects asset tag "IT-00421", when the resolution is submitted, then the incident becomes "RESOLVED" and a finance report for the period lists that resolution against asset IT-00421 together with its supplier and purchase date.
FR-11 Reporter Visibility of Own Requests Requester capabilities (PED §2) The system will show an authenticated reporter the list of requests they submitted, each with its own reference and its current status, and will show no other reporter's requests. Given reporter A has submitted three requests and reporter B has submitted two, when reporter A opens their request history, then exactly three requests are listed, each with reporter A's own reference and the current status of the incident it belongs to, and none of reporter B's requests appears; and given reporter A submits a fourth request, when reporter A's history is reloaded immediately afterwards, then the fourth request is present.
FR-12 Overdue Request Visibility Management and oversight capabilities (PED §2) The system will assign each incident a resolution due time derived from its priority at the time it is opened, will recalculate it when the priority is overridden, and will allow management to list incidents that are still open past that time. Given the response target for priority 2 is one working day and an incident was opened with priority 2 more than one working day ago and is still open, when a manager opens the overdue list, then that incident appears with its due time and the elapsed overrun; and given a supervisor then overrides its priority to 1 whose target is four hours, when the incident is reloaded, then its due time is four hours after the original opening time, not four hours after the override.
FR-13 Automated Notifications on Status Change Requester capabilities The system will dispatch a notification to the original requester whenever their service request transitions to an accepted, rejected, updated, or completed state Given a service request currently in the "ASSIGNED" status, when an authorised staff member changes the status to "RESOLVED", then a notification containing the resolution summary, the new status, and the request reference is successfully dispatched to the reporter.
FR-14 Role-Specific Staff Request Queue Staff capabilities The system will restrict the default request queue for authenticated staff members to only show service requests relevant to their authorised department, team, or direct assignments. Given an IT support technician logs in, when they access the active request queue, then they only see requests categorized under "IT Support" or requests explicitly assigned to them, and do not see requests routed to "Facilities" or "Security".
FR-15 Search, Filter, and Sort Service Requests Staff capabilities The system will allow authorised staff to search requests by keyword, filter the list by category or status, and sort the results by priority or date. Given a queue of 50 active requests, when a staff member applies a filter for the "Electrical" category and sorts by "Priority (High to Low)", then the interface updates to display only Electrical requests, with priority 1 requests appearing at the top of the list.
FR-16 Record Ongoing Actions and Comments Staff capabilities The system will allow authorised staff to append timestamped comments and action logs to an active ticket without requiring a formal status transition Given an open service request, when an assigned staff member submits the comment "Awaiting parts delivery", then the comment is appended to the ticket's detailed history alongside the staff member's identity and a timestamp, and the ticket's status remains unchanged.
FR-17 Management Dashboard and Categorical Reporting Management/oversight capabilities The system will provide management with an aggregated view of service activity, identifying open, overdue, resolved, and closed requests, filterable by category and time period. Given a manager accesses the oversight dashboard, when they filter by the current month, then the system displays a numerical breakdown of total requests grouped by category, alongside a summary of their current aggregate statuses (e.g., 10 Open, 5 Resolved, 20 Closed).
