Architecturally Significant Requirements & Quality Drivers

PED v2.0 §6.1. Six requirements that force a structural decision — an enforcement boundary, a transaction shape, a storage guarantee or a deployment constraint — rather than one component's internal logic.

ASR-01 — Role-based authorisation and least privilege

Evidence from the PED

The in-scope capabilities describe four capability groups (requester, staff, management and oversight, configuration and administration). Each has different authority over the same entities. Staff "can see service requests which they are authorised to see" and "assign responsibility on an authorised basis". The PED says "all changes to the configuration should be made by only authorised users". Information Regulators will "oversee the lawful processing of staff personal information". The Security row in the scope constraints asks for "authentication, authorisation, sensitive information, least privilege". NFR-01 already loads the JWT secrets and the database connection string from environment variables.

Measurable expectation
  • Given a user in the requester group only, when they call the status-change endpoint, the call is rejected, the status is unchanged, and no history record is added.
  • Given a supervisor authorised for one service team, when they change the status of a request assigned to another team, the call is rejected. The response says whether the cause is the role or the team scope.
Design implications
  • One enforcement point. Identity, roles and team scope are checked once at the API boundary, before domain logic runs. This is a single middleware, not a check in every handler. OWASP recommends application-wide configuration, a check on every request, deny by default, and server-side enforcement only (OWASP, 2026).
  • Roles and teams as tables. Store them as relations, not a free-text role on the user. The staff- and management capabilities describe two scopes over the same rows.
  • Least privilege in the database. The application's database account gets only the privileges it uses, per table, never ALL PRIVILEGES. PostgreSQL supports this through GRANT. It depends on FEC-01 choosing a relational database. It complements the application check but does not replace it, because a single connection cannot express per-user row access. That split is team judgement.
  • Signed tokens. A JWT carries identity and role claims, so a request needs no extra database call. The signing key comes from an environment variable (NFR-01).
  • RBAC is enough. OWASP prefers attribute-based or relationship-based control because RBAC suffers role explosion, but concedes it works for simple systems (OWASP, 2026). CivicConnect has six roles (reporter, technician, team leader, operations manager, finance, admin). The out-of-scope section excludes multi-tenancy. RBAC plus one team-scope check is enough, and a full attribute engine would strain Team Size and Schedule.

ASR-02 — Incident consolidation and subscriber notification

Evidence from the PED

STK-CFL-01: "if urgency is self-declared, everything will be declared urgent". Priority is instead "calculated off impact and urgency, based on the reported location and category", with a supervisor override and "a recorded reason". STK-CFL-02: every reporter expects acknowledgement, but "technicians need to resolve just one incident". Related reports are grouped under one parent incident and every reporter subscribes to it. STK-02 says technicians will not get repeated alerts for the same issue. FEC-01 leaves the relational-versus-NoSQL choice open because the system needs "transitions for request statuses and safe storage of user data".

Measurable expectation
  • Given an open parent incident for "Network outage" at "First Floor", when another reporter submits the same category and location, no new parent is created. The report count rises by exactly one, the reporter gets their own reference, and they appear in the subscriber list once, even if their client retries.
  • Given twenty reporters submit the same category and location in one second, there is exactly one open parent, each reporter appears in its subscriber list once, and technicians see one work item.
Design implications
  • One transaction. "At most one open parent per category and location, one subscription per reporter" cannot survive replication lag, because a duplicate would mean a technician is notified twice. Submission therefore runs as one aggregate in one transaction, not across separate services or pipelines.
  • Enforce it in the database. Check-then-insert is racy under PostgreSQL's default Read Committed isolation, where consecutive SELECT statements can see different data. A partial unique index on the clustering key, limited to open rows, plus an atomic ON CONFLICT DO UPDATE upsert guarantees one outcome even under high concurrency. The upsert needs the index as its conflict target, so the two are one decision. It depends on FEC-01.
  • Observer pattern. Reporters subscribe to the parent incident, and each state change notifies every subscriber (Gamma et al., 1994). The subscriber list also backs each reporter's own reference, so acknowledgement and notification stay in sync.
  • Safe retries. Submission is a create, so it is not idempotent by method (Fielding, Nottingham & Reschke, 2022, §9.2.2). A client-supplied submission key, stored server-side, with replays returning the stored result, is proposed — the PED says nothing about retries.
  • Computed priority. Priority comes from category and location, not from the reporter. The supervisor override carries a recorded reason, so it is an auditable write. This links to ASR-05.

ASR-03 — Bounded configurability without a rules engine

Evidence from the PED

The PED specified that administrators could create, update, activate or deactivate categories "without impacting the existing request data". Changes "should not delete or overwrite historical request data that would provide accountability". The aim is "controlled configurability at the office level instead of any system customization", and CivicConnect "was never meant to work as a generic no-code application building tool". The scope constraints repeat this: any office should be supported "without becoming a no-code, workflow builder or multi-tenant platform". ASM-06 assumes that is "achievable via a well-controlled combination of configurable components including categories, operational scope and role".

Measurable expectation
  • Given an administrator creates a category with a default team and urgency, when it is saved, it is immediately selectable on the submission form and used in priority calculation for new requests, with no code change or redeployment.
  • Given an administrator deactivates a category that historical requests use, when they confirm, no historical request is changed or deleted, and past reports still show the category.
  • Given an administrator looks for a way to add a form field or a status transition outside the documented set, when they search the product, no such feature exists. This is intended under the out-of-scope section of the PED, not a bug.
Design implications
  • Configuration is data, not code. Categories, areas, teams and roles are rows in one shared schema, with no office-specific code branches or schema variants. Deactivating a category changes its state and never deletes it, so configuration rows fall under ASR-05's accountability rules. This is our reading of ASM-06 and the admin capabilities.
  • Strategy pattern, not a rules engine. Priority calculation (STK-CFL-01) is one named algorithm behind one interface, and administrators set only its inputs. The formula can be replaced without changing the code that calls it.
  • No user-authored logic in the stack. No scripting runtime, expression interpreter or workflow-definition language. Adding a library for that purpose expands scope and needs a scope control impact assessment.
  • Where variability lives. Configurability depends on whether variability sits in external data or in compiled logic, not on how much of it there is. ASR-03 applies that to CivicConnect.

ASR-04 — Cost-constrained, portable, container-deployable operability

Evidence from the PED

The scope constraints Cost row says, "free or low-cost services must be preferred when possible, and potential operational costs and platform capabilities must be known". ASM-03 assumes deployment technologies that "will not cost too much". RSK-01 is the main risk: "platform limitations may restrict deployment and cause unexpected downtime", caused by "unanticipated operational costs or exceeding free-tier resource limitations". Its mitigation is to document "resource limits for Docker containerisation deployments early", and its contingency is to "migrate the chosen backend to an alternative low-cost hosting provider". FEC-02 says CivicConnect "requires logging, monitoring, health checks and failure detection before staging and launching to production", and defers only the choice of tool. §6.6 forbids committing secrets, and NFR-01 restates that as an acceptance criterion.

Measurable expectation
  • Given the application is a container image with all environment-specific values in environment variables (NFR-01), when it is redeployed to a different low-cost host, it starts and serves requests with no source-code change.
  • Given the running application, when an operator or hosting probe queries the health endpoint, it reports within a bounded time whether the application and its database are healthy (FEC-02).
Design implications
  • Stateless single deployable. No in-memory sessions, no server affinity, no reliance on host-local files. Changing provider is then a redeploy, not a rewrite. Containers contain everything needed to run the application and run on laptops, data-centre machines and clouds alike. That is why RSK-01 names Docker.
  • Container plus external configuration. The container makes the runtime portable, and environment variables make the behaviour portable. The twelve-factor approach keeps config in environment variables, separate from code — NFR-01 covers secrets only. We propose applying it to every value that varies by environment, such as the database host and provider limits, as NFR-13.
  • Observability as a seam. FEC-02 defers the tooling, not the obligation. We commit now to a health endpoint and a single logging abstraction, so a later tool choice is only a configuration change. OWASP says logs should record "when, where, who and what", and that passwords, tokens and session identifiers "should usually not be recorded directly in the logs" (OWASP, 2026d). This links to ASR-06.
  • Cost applies to the database too. Cheap application hosting with an always-on replicated database would break the same constraint. We propose one answer for both tiers: accept bounded downtime and protect data with backups.

ASR-05 — Concise-but-traceable capture with a system-generated audit trail

Evidence from the PED

STK-CFL-03: technicians want "to resolve a ticket as quickly as possible with minimal typing", while finance wants "a detailed report with as much traceability to physical goods and hardware as possible". The resolution is to make "the report a technician must fill in as concise as possible while retaining all relevant and important data". Technicians need minimal typing "as to not impede ticket closure times", and finance "will monitor data of broken equipment for claims and budgeting purposes". Management "see request history and audit details". Configuration changes "should not delete or overwrite historical request data that would provide accountability". STK-CFL-01 requires a supervisor's priority override to carry "a recorded reason".

Measurable expectation
  • Given a technician resolves a request by picking an outcome and an equipment identifier and typing a short summary, when finance runs a claims report, it lists the resolution against the correct equipment and supplier, using the structured selections.
  • Given any priority override, status change or configuration deactivation, when a manager opens the audit trail, an entry shows who acted, what changed, when, and the old and new values. The system writes it, and no user logs anything by hand.
Design implications
  • Solve the conflict in the schema. Required structured fields (outcome, equipment link, short summary) sit apart from optional free text. The equipment link is mandatory only where finance needs it for claims. With free-text resolutions, finance would have to parse prose, and fixing that later means reprocessing history. This is our proposal.
  • The write path creates the audit entry. The operation that makes a change also writes its audit entry. Users type less, and traceability still happens. Each entry records "when, where, who and what" (OWASP, 2026).
  • Append-only through privileges. A coding convention cannot guarantee administrators "should not delete or overwrite". We propose giving the application's database role SELECT and INSERT on the audit table but not UPDATE or DELETE, using PostgreSQL's per-privilege GRANT. This depends on FEC-01.
  • Keep personal data out. Requests carry personal information, so OWASP's rule to "never log data unless it is legally sanctioned" applies to the audit payload too (OWASP, 2026).

ASR-06 — Access-controlled publication of unresolved incidents

Evidence from the PED

STK-CFL-04: "Users want reports that were already made to be visible, whereas the operations manager would prefer not to display a list of unresolved issues". It is resolved in favour of publication: "the argument for publishing the data is stronger than against; however, it is also possible to publish resolution statistics per category". Requester capabilities let requesters see their own requests and history. Staff capabilities limit staff to "service requests which they are authorised to see". STK-06 oversees "the lawful processing of staff personal information".

Measurable expectation
  • Given an unresolved incident, when any authenticated user views the published list, they see category, location, status and priority. Reporter identity, assignee identity and internal notes are absent from the response payload, not just hidden by the client.
  • Given the same incident, when a staff member on the assigned team views it, they also see the assignee, the notes and the full status history.
  • Given a request for per-category resolution statistics, only aggregate counts come back, with no identifiers.
Design implications
  • One store, one projection per audience. The published list, own history, team queue and management analytics each expose different fields from the same data, gated by the ASR-01 enforcement point. A separate public copy would need its own sync, access control and privacy review, which the Team Size constraint cannot fund. A second read model would also bring back the staleness ASR-02 removed. The PED sets no read-throughput target that would justify it.
  • Classify fields first. Every attribute a read path can reach is classified for personal information and recorded on the data model. Inclusion in the published projection is opt-in per column, so adding a column cannot widen exposure. POPIA is cited at Act level only, because its PDF could not be text-extracted. The Regulator's own mandate carries the enforcement claim.
  • A separate endpoint, not a flag. The published list has its own endpoint and narrower response shape. OWASP says developers "must never rely on client-side access control checks" (OWASP, 2026), and a field hidden in the browser has already crossed the network.
  • Statistics as the fallback. Per-category statistics are an aggregate query with no row identifiers. Kept as their own projection, they let us respond to a reversal of the publication decision by changing routing, not redesigning.
