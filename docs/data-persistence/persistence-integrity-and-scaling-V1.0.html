Persistence, Integrity & Scaling

PED v2.0 §6.3.5–6.3.6. The persistence-technology decision, the ten-year growth estimate, the transaction and concurrency rules, and the bottleneck/backup posture for the CivicConnect database.

4.1 Decision and Justification

The system uses one PostgreSQL 16+ database as a single logical instance, with the schema enforcing the invariants and the service holding the business rules. The design has 21 tables with fixed columns, and the PED rules out user-defined fields, so configurability lives in rows and not in table shape. Thirty foreign keys keep related tables consistent. A foreign key "specifies that the values in a column (or a group of columns) must match the values appearing in some row of another table" (The PostgreSQL Global Development Group, 2026). Management reporting needs ad-hoc aggregation by status, category and age. Twenty-seven declarative constraints, six of them partial unique indexes, carry the stakeholder-conflict resolutions. Six multi-entity operations must be all-or-nothing, which single-node ACID with Read Committed plus constraints handles. The data is personal information under POPIA, so it needs table-level grants, a credential table the reporting role cannot read, TLS and a retention mechanism, and PostgreSQL documents all of these. Growth is predicted to be small (§4.2 below), so retention and not size is the trigger for revisiting the design.

Five alternatives were rejected. A document store such as MongoDB, Firestore or DynamoDB loses its flexible schema advantage the moment the clustering invariant is written as a partial unique index. MongoDB's own manual says distributed transactions should not replace effective schema design (MongoDB, Inc., 2026), and without foreign keys merged_into_id and root_incident_id could break silently so that a fan-out query returns nobody. A polyglot split, with a document store for audit and notifications, adds a second system to back up and secure for a flexibility that jsonb already gives, and it breaks the guarantee that an audit row commits with the change it records. SQLite allows only one writer at a time per database file (SQLite, 2025), which fails the PED's mass-report scenario. MySQL and MariaDB have no partial indexes (Oracle, 2026), so six invariants, including the clustering rule, would become generated-column tricks that a reviewer can't read at a glance. SQL Server can do all of it, with filtered indexes, rowversion for optimistic concurrency (Microsoft, 2026) and range-locking serializable isolation, but it fails on cost and hosting under RSK-01 because none of the free tiers offers it.

4.2 Growth Estimate

These figures are estimates, and each assumption is stated so it can be challenged. The system serves 250 requesters in one office and 12 service staff. The team's judgement, with no client figure to back it, is 30 submissions per working day over 250 working days, which gives 7,500 tickets a year. Also by team judgement, tickets cluster at 1.25 per incident, which gives 6,000 incidents a year. Each incident goes through 5 status transitions on the typical path and collects 2 notes. Each ticket sends 4 notifications (acknowledgement, assigned, resolved, closed). Each incident writes 12 audit rows (create, cluster, claim, five transitions, override, resolve, close and merge), and login-driven configuration and auth events add another 5,000 audit rows a year.

Those assumptions put the yearly load at about 176,000 rows and 75 MB of table data. The audit log is by far the largest at 77,000 rows and 54 MB, because each row averages about 700 bytes with its two jsonb payloads. The next largest are notifications at 6 MB, notes at 4.3 MB, tickets at 4.2 MB and status history at 3.6 MB. Resolutions, incidents and subscriptions add about 3 MB between them, and submission_request is negligible at about 150 live rows. Indexes add about 45 MB, roughly 60 percent of the table data for this index set. With headroom for bloat, the total is 120 to 140 MB a year. Over ten years that is about 1.3 GB and 1.8 million rows, with the audit log making up about 72 percent of the bytes. If the submission rate is wrong by a factor of ten, the ten-year size is about 13 GB, which is still an ordinary PostgreSQL database.

5. Integrity, Transactions, Concurrency

A transaction "bundles multiple steps into a single, all-or-nothing operation", so if one step fails "none of the steps affect the database at all" (The PostgreSQL Global Development Group, 2026). Everything runs at Read Committed, PostgreSQL's default, which the manual calls adequate for many applications.

Standing rules

Unique indexes prevent duplicates, not the isolation level, because an index stops every writer, including one that bypasses the service. One service operation is one transaction, and no repository commits on its own. Every UPDATE incident checks version and then increments it. The application retries serialization failures and deadlocks up to three times, but never a unique violation, which is a business outcome. Locks are taken in a fixed order to avoid deadlocks and no HTTP call or wait on a user happens inside a transaction.

Submitting a request

The submission is one transaction. It reads the chosen category and location with FOR SHARE, which blocks a concurrent deactivation, and answers 409 if either is inactive. It inserts into submission_request, and if that key already exists the request is a replay, so the stored result is returned. A single statement then clusters or creates the incident: INSERT ... ON CONFLICT (category_id, location_id) WHERE status IN (open) DO UPDATE SET report_count = report_count + 1. The transaction then adds the ticket, the subscription, an opening history row if it created the incident, an acknowledgement notification and an audit row.

The check and the write are one statement, so there is no gap for a second reporter to slip into. Any error rolls everything back, so a ticket never exists without its incident. A client that misses the response retries with the same Idempotency-Key and gets the original result.

Claiming, transitions and overrides

A claim is one conditional UPDATE that matches only if the version is current, the incident has no assignee and its status is NEW. If no row matches, someone else got there first, and the service answers 409 and does not retry.

A status change is checked before any SQL runs. The update then guards on the version and the from-status, and the history row is written in the same transaction. A priority override sets the priority, reason, actor and time in one update and recomputes due_at. Only a supervisor on the incident's team may do it. incident_override_ck rejects an override without a reason, and the version check stops a recalculation from silently reverting it.

Resolving and deactivating

Resolving is one transaction. It supersedes the current resolution, inserts the new one, moves the incident on, notifies every subscriber (including those attached by a merge) and writes an audit row. resolution_current_uq allows only one current resolution, and a replacement claim must name an asset. Deactivating a category is never blocked by open incidents.

Validation layers

The request schema checks that a request is well-formed. The service checks that it is the right business outcome, and owns the transition matrix, role authority and priority arithmetic. The database guards what must be true of the stored data whoever wrote it. Client-side checks are for usability only. The database enforces an invariant when it must never be false, can be written declaratively and could be broken by a race. That covers the clustering index, the idempotency key, one subscription per reporter and incident, one current resolution, the override and timestamp checks, the replacement-needs-asset rule, foreign keys, and append-only audit and history.

6. Bottlenecks, SPOF, Scalability, Availability, Backup and Recovery

For CivicConnect, scaling isn't a concern at the volume. What could hurt a small team on free services (RSK-01) is losing data, so backup and restore are the priority.

One PostgreSQL instance holds everything, and if it fails the whole system fails. This is accepted on purpose. A replica with automatic failover would prevent data loss, but it doubles the hosting bill and needs skills the team lacks. If availability requirements tighten, the first step will be a cheaper asynchronous standby. For now the control is a backup that has been tested by restoring it.

The other scaling risks are small. With 30 submissions a day, 10 to 20 application connections are enough. Every transaction is short, and the supervisor's override, the one human decision, uses a version check and not a held lock, so old row versions won't pile up. In a mass event, reports for the same category and location queue on one incident row. At 100 transactions a second, 200 reports clear in about two seconds. That lock is what prevents duplicates, so it stays (RSK-09). Read replicas are not needed, but if they are added, the reporter's history and the staff queue must stay on the primary — a reporter who can't see their ticket will submit it again, and a stale queue can send two technicians to the same fault.

The audit log is about 70 percent of the bytes, so retention sweeps come first, followed by monthly partitions if deletion slows down. Every index slows writes, so before adding one to incident, usage of the existing ones should be checked.
