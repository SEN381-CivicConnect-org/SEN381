Data Model & Lifecycle

PED v2.0 §6.3.1–6.3.3. Aggregate boundaries, ownership, entity lifecycle, the merge/clustering mechanism, and schema conventions for the CivicConnect persistence baseline.

1.1 Aggregates and Roots

An aggregate here means one consistency boundary: one transaction, one root, and no write to an interior table except through that root's service. The boundaries below are drawn where invariants are: each aggregate owns exactly the set of tables that one transaction must write together, and nothing more. This buys the property the PostgreSQL manual states of a transaction: it "bundles multiple steps into a single, all-or-nothing operation", and "the intermediate states between the steps are not visible to other concurrent transactions" (The PostgreSQL Global Development Group, 2026). Which tables fall inside which boundary is team judgement, unsourced, and is argued below rather than asserted.

1.4 Merge and Clustering Lifecycle

Two separate mechanisms handle duplicate reports.

Automatic clustering at submission. If a new submission matches an open incident on (category_id, location_id), it attaches to that incident instead of creating one. report_count goes up by one, and the system adds a new ticket and a new incident_subscription. The partial unique composite key between incident_id and reporter_id enforces this, so no lookup is involved.

Manual merge by a supervisor. Sometimes the clustering key misses two incidents that are really one event — a network fault might be reported under both "Network outage / First Floor" and "Account access / First Floor". The supervisor merges the absorbed incident into the surviving one in a single transaction:

  • The absorbed incident gets status = 'MERGED', merged_into_id set to the survivor, root_incident_id set to the survivor's root, closed_at = now() and version + 1.
  • The survivor's report_count increases by the absorbed incident's report_count, and its version goes up by one.
  • One incident_status_history row is added to the absorbed incident.
  • Each subscriber of the absorbed incident gets one MERGED notification.
  • One audit_log row is written with action = 'MERGE'.

Subscriptions are never re-pointed to the survivor. The primary key is (incident_id, reporter_id), so moving a subscription can collide with a row that already exists on the survivor. The only fixes are to delete the losing row, which destroys history, or to write a guarded UPDATE ... WHERE NOT EXISTS, which is easy to get wrong. Instead, each subscription keeps pointing at the incident it was created against, and notifications resolve the target through COALESCE(root_incident_id, incident_id):

-- every reporter who must hear about incident :id, including via merge chains
SELECT DISTINCT s.reporter_id
FROM incident_subscription s
JOIN incident i ON i.incident_id = s.incident_id
WHERE COALESCE(i.root_incident_id, i.incident_id) = :id;

root_incident_id is a denormalised pointer set at merge time, so finding an incident's root takes one join instead of a recursive CTE. If A is merged into B and B was already merged into C, A's root is set to C, so chains stay flat.

Foreign keys make sure these pointers land on rows that exist. A foreign key constraint "specifies that the values in a column (or a group of columns) must match the values appearing in some row of another table", which "maintains the referential integrity between two related tables" (The PostgreSQL Global Development Group, 2026). Without that check, merged_into_id and root_incident_id would be two unchecked pointers into the same table. One bad write would send the notification fan-out query to nobody, and no error would appear.

report_count is a stored counter, not a count(*) over ticket. The same INSERT ... ON CONFLICT DO UPDATE that does the clustering also updates it. The row lock that serialises concurrent submissions is the same lock that protects the increment, so the counter adds no contention. Deriving the count would give the same answer, but every queue render would have to aggregate over ticket — the queue is the most frequent staff read.

2.1 Conventions

ConventionValueReason
Engine PostgreSQL through the Npgsql EF Core provider. The first migration enables the citext extension. E-mail matching needs to ignore case, and citext does that.
Migration tool EF Core migrations. Each file is named <timestamp>_<Description>.cs and has an Up method and a Down method that undoes it. Anything EF cannot express, such as extensions and grants, goes in migrationBuilder.Sql(). Up and Down list the tables, columns, keys and indexes in plain code, so a PR reviewer can read them. The generated .Designer.cs and model snapshot files are not reviewed line by line. The content of this section is the contract, not the tool.
Location src/CivicConnect.Data/Migrations/ Migrations sit next to the DbContext and entities they describe.
Naming Identity columns (GENERATED BY DEFAULT AS IDENTITY). bigint for high-volume tables (team_member), integer for configuration tables (service_team), smallint for small lookup tables (role, team_role). app_user uses uuid with gen_random_uuid(). user_role uses the composite key (user_id, role_id). Identity columns are standard SQL and avoid serial/sequence-ownership quirks. app_user keeps uuid because user ids appear in tokens and URLs. BY DEFAULT lets seed rows carry fixed ids.
Timestamps timestamptz everywhere, mapped to DateTimeOffset, with now() as the database default. PostgreSQL stores these values as UTC and converts them to the session zone on output.
Text text for strings and citext for e-mail. The current schema sets no length limits. If a limit matters to the business, it can be added as an explicit bound.
Deletion ON DELETE RESTRICT on every foreign key (ReferentialAction.Restrict). Prevents deletion of a referenced row.
Audit columns created_at and updated_at on mutable tables, both defaulting to now(). Lookup tables have created_at only. user_role records granted_at and granted_by_user_id. app_user uses is_active and team_member uses left_at. Edited rows need both timestamps. Seeded lookup rows change only in a migration, so an updated_at column there would never move. A role grant is never edited, so it records who granted it and when. Rows are never deleted, so is_active and left_at mark when a user or membership ends.

Each migration covers one slice of the schema, so a reviewer can take one aggregate at a time. EF generates the tables and columns, and a reviewer checks them by reading the diff. The invariants EF cannot infer, such as partial unique indexes and CHECK constraints, need the real scrutiny. Each one gets an explicit name and a comment inside the migration, so a reviewer can find and challenge it without reading the whole schema. That supports the two-non-author-approval rule in the PED, because the partial unique index and the override constraint carry the stakeholder-conflict resolutions. EF applies migrations in timestamp order and records which ones have run in its history table, so the split is safe to rely on.

The three invariants that carry the design, as they would appear in the migration:

// Clustering invariant (STK-CFL-02). Only one open incident can exist per
// category and location. Submission relies on this: when a new report hits
// the index, INSERT ... ON CONFLICT attaches it to the existing incident.
migrationBuilder.CreateIndex(
    name: "incident_one_open_per_scope_uq",
    table: "incident",
    columns: new[] { "category_id", "location_id" },
    unique: true,
    filter: "status IN ('NEW','ASSIGNED','IN_PROGRESS','ON_HOLD')");
// Override invariant (STK-CFL-01). A reason that can be null will be null.
migrationBuilder.AddCheckConstraint(
    name: "incident_override_ck",
    table: "incident",
    sql: @"(NOT priority_overridden
              AND override_reason IS NULL AND override_by IS NULL AND override_at IS NULL
              AND priority = computed_priority)
        OR (priority_overridden
              AND override_reason IS NOT NULL AND btrim(override_reason) <> ''
              AND override_by IS NOT NULL AND override_at IS NOT NULL)");
// One current resolution per incident. Superseded resolutions are kept and
// have no limit.
migrationBuilder.CreateIndex(
    name: "resolution_current_uq",
    table: "resolution",
    column: "incident_id",
    unique: true,
    filter: "superseded_at IS NULL");
